Real files written by Bambu Studio, not by NSO, so the reader is tested against
someone else's structure and not just its own output.

| file | source | structure |
| --- | --- | --- |
| `pa_pattern.3mf` | Bambu Studio repo, `resources/calib/pressure_advance/pa_pattern.3mf` (BambuStudio-01.07.03.04) | Production extension: one wrapper object whose `<component p:path>` points at `3D/Objects/Cube_1.model`; the build item carries a **non-uniform scale** (an 18 mm cube squashed to 5 x 5 x 0.85 mm); names in `Metadata/model_settings.config` |
| `flowrate-test-pass2.3mf` | Bambu Studio repo, `resources/calib/filament_flow/flowrate-test-pass2.3mf` | Older layout: ten objects with **inline meshes** in `3D/3dmodel.model`, material-extension colour groups interleaved, build items with **no transform attribute**, no `model_settings.config`, names on `<object name>`; the archive carries **ZIP64** end-of-central-directory markers |

## Synthetic fixture - toolpath ground truth

`toolpath-ground-truth.gcode.3mf` (with `toolpath-ground-truth.gcode.expected.json`)
is the one fixture here that Bambu Studio did **not** write. It is generated by
`tools/gcode-test/make-fixture.js` and it exists for a reason the real files
cannot serve: the toolpath importer's claim is that it recovers a move's printed
width from that move's own E value, and proving that needs a file whose correct
answer is known exactly. The generator is handed the width and height each line
should print at, runs the flow model forwards to get the E a slicer would have
written, and emits that; `npm run gcode:lines` then asserts the importer
recovers the widths and angles it started from.

It is deliberately structured like a real Bambu slice - `M83`, `G92 E0`,
`; FEATURE:` / `; Z_HEIGHT:` / `; LAYER_HEIGHT:` / `; CHANGE_LAYER`, travels,
retractions, Z hops, the trailing config block - so the parser meets the same
shapes. The geometry is a test pattern and no claim is made that Bambu would
slice anything this way. Regenerate with `npm run gcode:fixture`.

## Real sliced files - the toolpath importer's real-file tier

Two projects sliced by Bambu Studio, committed so the toolpath importer is
measured against files a slicer actually wrote and not only against the fixture
above:

| file | structure |
| --- | --- |
| `tabletop.gcode.3mf` | 73 layers, 202,877 moves, 9 features. A tree-support tower under a tabletop, whose support interface is **exactly two stacked layers** zigzagging in opposite directions at a 0.61 mm strand width, with no border feature. The three hand-verified measurements off this file are asserted in `tools/gcode-test/gcode-zfilter-check.js`. |
| `supportwithinsupport.gcode.3mf` | 50 layers, 2,895 moves, 10 features. The only one of the two that exercises `Floating vertical shell`, and small enough to read by hand. |

Both are the user's own sliced projects, staged on `nolongerzzz/nest-wip`
(branch `source-files`, folder `uploads`). They are not Bambu Lab or MakerWorld
content, so the licence note above that keeps a MakerWorld project out of this
directory does not apply to them.

`npm run gcode:lines` and `npm run gcode:zfilter` both read these by default -
the real-file tier no longer skips. `NSO_GCODE_REAL=/path/to/a.gcode.3mf`
overrides, to run the same measurements over another slice. See
`docs/GCODE-TOOLPATH-IMPORT.md` and `docs/GCODE-FEATURE-AUDIT.md`.
